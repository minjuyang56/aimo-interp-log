전체 그림

저장소는 두 종류의 코드로 나뉩니다. 채점하는 쪽은 대회 주최측 코드이고 당신은 손대지 않습니다. 채점당하는 쪽이 당신이 만들어 제출할 코드입니다. 이 경계가 저장소 구조 전체를 결정합니다.

이 구조가 중요한 이유는 Codabench 서버에서도 완전히 똑같이 돌아가기 때문입니다. 로컬의 run_local.py가 하는 일을 서버에서는 Codabench 플랫폼이 대신 합니다. 그래서 로컬에서 통과하면 서버에서도 통과한다는 보장이 생깁니다 — 단, 환경이 같을 때만.

구조가 말해주는 것

두 예제 솔루션 모두 solution.py가 10줄 안팎입니다. 진짜 코드는 옆 파일에 있죠. 일부러 그렇게 만든 겁니다 — 채점기가 검사하는 건 solution.py의 함수 하나뿐이라, 그 파일을 얇게 유지하면 계약을 어길 일이 없습니다. 당신도 이 패턴을 따르는 게 안전합니다.

실행 순서

uv run scripts/run_local.py solutions/trained-probe 한 줄을 치면 벌어지는 일을 순서대로 따라가 봅니다. 서버에서도 3번부터는 동일합니다.

  1. 임시 작업장을 만든다

    tempfile.TemporaryDirectory()로 폴더를 하나 파고, 정답 파일 labels.jsonl을 그 안 input/ref/로 통째로 복사합니다. 이 폴더는 실행이 끝나면 사라집니다. run_local.py:37-44

  2. 첫 번째 프로세스: 예측 수집

    ingestion.py를 새 파이썬 프로세스로 띄웁니다. 인자는 세 개 — 입력 폴더, 출력 폴더, 그리고 제출물 폴더. run_local.py:46-55

  3. 입력을 읽고 형식을 깐깐하게 검사한다

    load_cases()가 28줄을 한 줄씩 읽으며 id 중복, model_id 누락, problem 키가 정확히 original_problem과 permutation_type 둘뿐인지까지 확인합니다. 하나라도 어긋나면 즉시 중단. ingestion.py:35-66

  4. 당신의 solution.py를 메모리로 불러온다

    importlib.util.spec_from_file_location으로 파일을 직접 로드합니다. 그리고 are_robust의 함수 서명을 런타임에 검사합니다 — 인자 이름, 순서, 타입 힌트, 반환 타입까지 전부. 하나라도 다르면 거부됩니다. ingestion.py:69-124

  5. 같은 모델끼리 묶는다

    28건을 model_id별로 그룹화합니다. 우리 데이터에선 7개 그룹이 나왔습니다. are_robust는 그룹마다 한 번씩, 총 7번 호출됩니다. 모델을 한 번만 로드하고 여러 문제를 처리하라는 뜻입니다. ingestion.py:146-148

  6. 호출하고, 결과를 검사한다

    반환값이 list인지, 길이가 입력과 같은지, 원소가 전부 진짜 bool인지(넘파이 bool_이나 1/0은 탈락) 확인합니다. 예외가 나면 조용히 삼키고 그 그룹 전체를 valid=False로 처리합니다 — 에러 메시지는 어디에도 남지 않습니다. ingestion.py:156-179

  7. 예측을 파일로 쓴다

    predictions.jsonl에 케이스별로 {id, is_robust, valid} 한 줄씩. 여기서 첫 프로세스는 끝납니다. ingestion.py:181-190

  8. 두 번째 프로세스: 채점

    scoring.py가 새로 뜹니다. ref/에서 정답을, res/에서 예측을 읽어 대조합니다. 당신 코드는 이 프로세스에 아예 로드되지 않습니다. scoring.py:112-117

  9. 점수를 낸다

    accuracy의 분모는 전체 28건이지 맞힌 것만이 아닙니다. 즉 예외로 날린 케이스는 오답과 똑같이 정확도를 깎습니다. scoring.py:76-109

  10. 출력하고 작업장을 지운다

    run_local.py가 scores.json을 읽어 화면에 찍고, 임시 폴더는 사라집니다. run_local.py:65-66

의존 관계

누가 누구를 import 하는가. 왼쪽 끝의 채점기는 오직 solution.py 하나만 압니다 — 그 뒤로 뭐가 있든 상관하지 않습니다.

계약: 이 함수 하나

저장소 전체가 이 한 줄을 중심으로 조직돼 있습니다. 채점기가 런타임에 서명을 검사하므로 타입 힌트까지 글자 그대로 맞아야 합니다.

def are_robust(model_id: str, problems: list[str]) -> list[bool]:
    return [True, False, ...]  # 입력과 같은 개수, 같은 순서

예외는 삼켜집니다

are_robust 안에서 무슨 에러가 나든 채점기는 except Exception: pass로 넘어갑니다 (ingestion.py:169-171). 서버는 그 그룹을 통째로 무효 처리할 뿐, 이유를 알려주지 않습니다.

실제로 이 저장소에서 trained-probe를 돌렸을 때 invalid_predictions: 28만 나오고 원인은 전혀 안 보였습니다. 직접 are_robust를 불러봐야 “모델이 캐시에 없다”는 진짜 에러가 나왔습니다. 제출 전 로컬 디버깅이 필수인 이유가 이것입니다.

uncertainty-profiling 내부

완전히 다른 접근입니다. 모델에게 문제를 실제로 풀게 시키고, 푸는 동안 얼마나 확신에 차 있었는지를 토큰 단위로 기록합니다. “헷갈리면서 푼 문제는 흔들린다”는 가설이죠.

모듈 6개의 역할

config.py가 중심입니다 — 특징 14개의 이름과 순서를 상수로 고정하고, 생성 설정(프롬프트 2048토큰, 응답 4096토큰, 배치 8, 그리디 디코딩)을 담습니다. extraction.py가 생성을 돌리며 수집하고, metrics.py가 통계를 내고, artifact.py가 학습된 회귀모델을 꺼내고, inference.py가 넷을 엮습니다.

모델을 다루는 방식

inference.py는 모델을 배치당 한 번만 로드하고, finally 블록에서 release_model()로 반드시 해제합니다. 같은 저장소 안에서 trained-probe와 정반대죠. 이쪽이 올바른 패턴입니다.

수집하는 신호무엇을 재는가

이 방법은 실제로 점수가 나왔습니다

로컬에서 돌린 결과 accuracy 0.643, coverage 0.964, invalid 1. 모델이 캐시에 없는데도 대부분 살아남은 이유는 load_artifact()가 맞는 아티팩트를 못 찾으면 예외 대신 전부 False를 반환하기 때문입니다.

입력 28건의 model_id는 7종인데 번들된 아티팩트는 DeepSeek 하나뿐입니다. 그래서 27건은 “모르겠으니 False”로 조용히 넘어가고, DeepSeek을 요구하는 1건만 무효가 됐습니다. 모르는 입력에 우아하게 실패하는 설계가 점수를 지켜준 사례입니다.

확인된 문제

전부 실행해서 재현한 것들입니다. 추측이 아닙니다.

1. 모델을 문제마다 다시 로드합니다 고침

_encode_problem이 매번 _load_model을 호출하고 있었습니다 (수정 전 probe_inference.py:248). 아티팩트는 루프 밖에서 한 번만 로드하면서 모델은 안 그랬습니다. 서버에는 모델이 캐시돼 있어 로컬처럼 즉사하지 않고 시간 초과로 죽었을 문제입니다.

고친 방식: predict_robustness가 배치 시작 시 모델을 한 번 로드해 _predict_problem → _encode_problem으로 넘겨주고, finally에서 _release_model()로 해제합니다. 같은 저장소의 uncertainty-profiling이 이미 쓰던 패턴 그대로입니다.

모델 로드를 가짜로 바꿔 횟수만 센 결과입니다. 반환값 개수와 bool 타입은 양쪽 모두 계약을 지킵니다. 저장소 테스트 20개도 그대로 통과합니다.

2. 문서와 실제가 다릅니다
